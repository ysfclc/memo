## How to use this register

Each requirement has a stable ID. Keep IDs stable when wording is clarified; create a new ID when a genuinely new capability is introduced. Record changes in the Decision Log. A requirement may map to multiple engineering tasks and source files.

Statuses follow [../DEVELOPMENT_GOVERNANCE.md](../DEVELOPMENT_GOVERNANCE.md): specified, designed, in_progress, implemented, verified, device_verified, blocked, deferred, unknown.

**Evidence rule:** a source path proves only that code exists. Tests prove only the behavior they exercise. CI proves only the exact commit and checks reported. Real-account/device acceptance must be separately identified. Never promote a status based on a UI screen or a model's statement.

## Audit queue — do not infer completion

The following should be completed in order. Update the rows above with exact paths, test names, commit SHA and evidence links; split requirements if a domain proves too broad.

1. **Baseline refresh:** verify default branch, working branch, current head, open PRs, latest CI and whether the source audited by FEATURE_AUDIT still matches the current branch.
2. **P0 source/data audit:** stores, migrations, secrets, permission model, action approvals, global stop, external side effects and backup/deletion lifecycle.
3. **Journey audit:** Talk→plan→Live→Work→Studio; arbitrary workflow; capture; voice; CRM/person; job application; content; social; daily follow-through.
4. **UI audit:** inspect actual navigation/screens and trace every visible control to a real action, loading/error/empty states and localization.
5. **Test audit:** map each requirement to existing tests and missing failure-path tests; inspect current CI for exact commit.
6. **Device audit:** separate emulator evidence from real-device acceptance and list the steps requiring the user's phone.
7. **Closeout:** replace stale dates/statuses only with fresh evidence; retain old records and explain changes.
